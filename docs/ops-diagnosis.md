## 2. Recovery runbook

`aiden upgrade` commits its own result (step 8), so one commit holds the whole upgrade.

- **Bad upgrade commit:** `git reset --hard HEAD~1` → `npm install` → `npx @upstart13-com/aiden-cli doctor`.
- **If its migrations already ran (step 6):** resetting the code does **not** roll back the database. Restore the pre-upgrade backup, or write a reverse migration with `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script` and apply it with `prisma migrate deploy`. That is the method the rollback rehearsal used (`rollback-rehearsal.md`). Take a database backup before every real upgrade.
- **In-flight changes:** `git stash` → upgrade → `git stash pop`, or commit first. A real upgrade refuses a dirty tree anyway.
- **Need to ship meanwhile:** pin `@upstart13-com/aiden-*` to the last known-good version in `package.json`. This is a temporary exception to "never hand-edit SDK versions". Ship, then return to `aiden upgrade` once unblocked, so its codemods and migrations still run.
- **Always finish** with a green doctor (CVE scan included) and `bash scripts/smoke-local.sh` 7/7. `bash scripts/checkpoint.sh <label>` records both the doctor run and a dry-run.

## 3. "Request context empty in prod, works locally"

- **Root cause:** two copies of `@upstart13-com/aiden-logging` mean two `AsyncLocalStorage` stores. `withAuth` writes the request context into one; the logger or sink reads the other, finds nothing, and `requestId` / `userId` go missing.
- **Diagnose:** `npm ls @upstart13-com/aiden-logging` shows more than one _installed_ copy. Count real copies (`find node_modules -path "*@upstart13-com/aiden-logging/package.json"`), not npm's "deduped" back-references; `verify.sh` E4 does this.
- **Fix:** `npm dedupe`, or an `overrides` entry pinning one version.
- **DeskLine:** a single copy (`docs/evidence/npm-ls-logging.txt`, and `verify.sh` E4 on every run).

**The same symptom from a different cause, which DeskLine actually hit:** Next 16 bundles `instrumentation.ts` separately from route handlers. Sinks registered only there (`setAuditSink`, `setAIUsageSink`) were registered on a different module instance than the one routes use, so audit and AI-usage rows silently weren't written. The fix was to import the sink modules from the route graph (`src/lib/auth.ts` → `@/lib/audit`; `src/lib/ai.ts` → `@/lib/ai-usage`). If context or sinks work in one place but not another, check for duplicate module instances (bundles) as well as duplicate packages.
